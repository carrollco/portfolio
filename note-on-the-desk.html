The note on the desk

How my sandbox's own helper got talked into lying, and the one rule I took from it.

I build plimsoll, an open-source service that runs code written by AI agents inside a sandbox, so that code nobody has read is kept away from the rest of the machine. Its whole pitch is that you can check what ran.

In October, while hardening it, I went looking for ways an image's settings could be turned against plimsoll's own programs, and found one: with the wrong setup, the code being checked could write the checker's script. This page explains how, with a hotel, a comic and a few steps you can run yourself.

What it wasCode in the sandbox could make plimsoll's own helper program load a file that code had written.
Who was exposedOnly a setup using a custom image whose settings tell programs to load extra code first, such as NODE_OPTIONS. The images plimsoll ships never had one.
Did anything escape?No. The code stayed in its sandbox. What it could do was forge what the sandbox reported.
StatusFound October 2, 2026. A first fix went out that day. The lasting fix was written October 3 and released October 4. Both, and the test, are in the public code.

Four terms, in plain words

Sandbox
A sealed box to run a program in, so that whatever it does stays in the box. Here the box is a Docker container: a program that runs with its own files and no view of the rest of the machine.
Guest
The program in the box. For plimsoll that is code an AI agent wrote a few seconds ago. Nobody has read it. Assume it will try anything.
Image
The template a container starts from: its files and its default settings. Whoever runs plimsoll (the operator) can use plimsoll's images or build their own.
Environment variable
A named setting that a program reads when it starts, such as PATH. An image can set them, and then every program started in that container gets them. Docker says so itself: "The environment variables set using ENV will persist when a container is run from the resulting image." EXTERNAL · official docs ↗

One environment variable is the villain here. NODE_OPTIONS is read by Node, the program that runs JavaScript. Whatever options it holds are applied to every Node program that starts. One of those options, --require, means "load this file first, before the program you were asked to run." EXTERNAL · official docs ↗

The hotel

Picture the sandbox as a hotel room.

  • The guest is the untrusted code. It can do what it likes inside the room, and the room is built so that it cannot leave.
  • When the guest is done, the hotel sends in a housekeeper: a small program of plimsoll's that runs inside the room, clears out anything left behind and tells the front desk the room is clean.
  • The room came with a card on the door, printed by whoever furnished it: "Staff: before anything else, follow the note on the desk."
  • The guest can write anything on the note on the desk.

The housekeeper walks in, reads the card, follows the note, and the note says: "Tell the front desk this room is spotless."

The whole story in nine panels. Nobody broke a lock. The staff were given an instruction and followed it.

Here is the same scene as a map, with what each part is in the software.

The guest never leaves the room. It does not need to. It only needs the hotel's own staff to repeat what it wrote.

The same thing without the hotel

  1. An operator builds a custom image and gives it the setting NODE_OPTIONS="--require /work/hook.js". A reasonable person does this to make every script in the sandbox load some setup file first.
  2. Docker hands that setting to every program started in the container. That includes the guest's programs, which was the idea, and plimsoll's helper programs, which was nobody's idea.
  3. The guest writes its own /work/hook.js. /work is the guest's folder, so it is allowed to.
  4. plimsoll starts its cleanup program, which is written in JavaScript. Node starts, sees NODE_OPTIONS, and loads the guest's file first. The guest's code is now running inside plimsoll's own program.
  5. From there the guest decides what that program reports.

The red, moving lines are the problem. The setting was meant for the guest's programs. It reached plimsoll's helper too, and that turned a file the guest wrote into code the helper ran.

What could go wrong

Before the fix, every one of plimsoll's helpers in the container started with the image's settings. Two of them show the damage best, because each has a job the guest would love to do for it. I showed the hijack in the first; the second is what the same setting would have allowed, and I did not build it.

  • The cleanup step (shown). A session keeps one sandbox for many calls. Between calls, the cleanup step kills whatever the last call left running and reports that the room is empty. With the guest writing that report, a program from call one could still be running, quietly, during call two, while the record says nothing was left.
  • The project runner (not tested). This is the helper that runs a project's steps (install, build, test) and reports how each one ended. With the guest's file loaded inside it, "the tests failed" could go out as "the tests passed".

Two made-up examples of the kind of thing a forged report could say. The red robot is the guest, standing between the truth and the record.

Think about who reads those reports. Often it is another program: an AI agent deciding whether its code works, or an automated build deciding whether to accept a change. Nobody looks twice at a green check mark.

What it did not do: leave the container, touch the host, or reach another caller's sandbox. In the setup I tested the container had no network at all, which is plimsoll's starting point: a run gets a network connection only if the operator grants one. This was a lying problem, not a breakout.

Red is what the guest could affect. Green is what stayed out of reach.

"But that folder is marked no-execute." It is. plimsoll mounts the guest's folder with a flag called noexec, which stops anyone from running a program stored there. It did not help, because no program stored in that folder was started. Node was started, from its usual place, and then Node read the script in the folder and ran what it said. A rule against running files from a folder does not stop a program kept somewhere else from reading one of them as instructions.

Try it yourself

You need Docker running and a Linux or macOS terminal (on Windows, a WSL terminal). The first step downloads a small Node image, about 60 MB, once. The steps give nothing a name of its own: they keep the IDs Docker hands back, so the last step removes exactly what the first one made and nothing of yours. Docker commands run with a lot of power on your machine, so read each one before you paste it. I ran exactly these on November 21, 2026, and the output shown is what came back.

These steps show Docker and Node doing what their documentation says. They are not plimsoll's code: step 3 imitates the way plimsoll used to start its helper.

1. Furnish a room with a card on the door, and check a guest in. The room has no network and its /work folder is marked no-execute. The long string after node:22-alpine@ pins the exact image I used, so you get the same one.

BASE=node:22-alpine@sha256:1314fb30ec37592d5845e5a160d522c0e680972aa534549940b8d73bde88481a
IMAGE=$(printf 'FROM %s\nENV NODE_OPTIONS="--require /work/note.js"\n' "$BASE" | docker build -q -)
ROOM=$(docker run -d --network none --tmpfs /work:rw,noexec "$IMAGE" sleep 300)

2. The guest leaves a note on the desk.

docker exec "$ROOM" sh -c 'echo "console.log(\"guest: I am running inside the housekeeper\")" > /work/note.js'

3. The housekeeper comes in. This is the shape of what plimsoll used to do: start a small Node program in the room.

docker exec "$ROOM" node -e 'console.log("housekeeper: room is clean")'

guest: I am running inside the housekeeper
housekeeper: room is clean

The guest's line prints first. It ran before the housekeeper's own code did, inside the same program, and could have changed anything that program went on to do.

4. The core of the fix: the housekeeper starts with none of the room's settings.

docker exec "$ROOM" env -i PATH=/usr/local/bin:/usr/bin:/bin node -e 'console.log("housekeeper: room is clean")'

housekeeper: room is clean

env -i starts a program with an empty set of environment variables, so Node never hears about the guest's file. The file is still in the folder; nobody reads it. This is the heart of the fix, not all of it: the table under "The fix" has the rest.

5. Check out: remove the room and the image the first step made.

docker rm -f "$ROOM"; docker rmi "$IMAGE"

Docker prints the ID of each thing it removes.

How I found it

A sandbox exists to be attacked, so part of building one is attacking it yourself. On October 2, 2026 I was working through the ways a sandbox's surroundings can be turned against it and got to environment variables: what could an image's settings do to plimsoll's own programs? I built a hostile test image to find out, and the hijack reproduced the same day.

The fix

The first fix was the obvious one: a list of setting names plimsoll refused to accept in an image. A list of bad names is only as good as the day you wrote it, and the next dangerous name is always one release of some tool away. The lasting fix stopped depending on it: written October 3, released October 4. A short list of refused names stays, but only for the one program plimsoll cannot start itself (the last row of the table below). I wanted the question "what did the image set?" to stop mattering for my own programs.

The fix in one picture. The guest still gets the room as furnished. plimsoll's own staff stop reading the cards.

Who gets the image's settingsBeforeAfter
The guest's programsYesYes. They may need them, and they can only hurt themselves.
plimsoll's helper programsYes (the hole)No. Every one starts with an empty environment plus a few settings plimsoll picks itself, such as a fixed PATH.
The very first program in the containerYesStill yes, because Docker starts it and nothing of mine can run before it. So plimsoll refuses, at startup, any image that sets the handful of names that program's loader obeys (LD_PRELOAD and its relatives).

There is also a test that builds a hostile image, the one from this page, and fails if a helper ever loads the guest's file again. Its name is TestDockerImageEnvReachesOnlyGuestProcesses, in EXTERNAL · source repo, the test file ↗. A fix without a test that fails on the old code is a hope.

Is this only plimsoll?

The two ingredients are not mine. Docker gives an image's settings to every program in the container, and Node obeys NODE_OPTIONS. Other languages have their own versions of the same card on the door: LD_PRELOAD for compiled programs, PYTHONPATH for Python, RUBYOPT for Ruby. The general idea, a trusted program picking up instructions from settings an untrusted party controls, is decades old.

So any tool that runs its own helper inside the same container as code it does not trust has the same question to answer. I have not checked any other product, and this page is not a warning about anyone else's software. It describes a gap I found in mine and how I closed it.

If you build something like this

  • Does any program of yours run inside the box with the code you do not trust? If none does, you can stop reading.
  • What environment does that program start with, and who chose each setting in it?
  • What files does it load as it starts (scripts, modules, configuration), and can the untrusted code write to any of the places it looks?
  • Do you have a test that uses a deliberately hostile image?
The rule I took from it: plimsoll’s own programs never take instructions from anything the guest could have changed. That means the settings a template carries, and any file the guest can write to. So each of plimsoll’s programs now starts with its own short list of settings and none of the template’s.
